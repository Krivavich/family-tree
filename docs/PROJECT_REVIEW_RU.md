# Критическая ревизия проекта (взгляд со стороны)

Документ написан как «аудит стороннего критика»: что было спорно, что исправили, что остаётся в рисках.

## 1) Спорные решения, которые были в проекте

1. **2FA verify без обязательного challenge_id для email/sms**
   - Риск: верификация могла работать по «последнему коду», что неявно и уязвимо к ошибкам UX/сессий.
   - Исправление: для non-TOTP теперь обязателен `challenge_id`.

2. **Trusted device без строгой привязки к fingerprint**
   - Риск: токен сам по себе мог использоваться на другом устройстве.
   - Исправление: валидация учитывает `user-agent` и `ip` (если заданы), обновляет `last_used_at`.

3. **Reject proposed change без транзакционного lock**
   - Риск: гонки при параллельном модераторском действии.
   - Исправление: reject переведён на `transaction.atomic + select_for_update`.

4. **Слабая прикладная защита auth endpoint-ов от brute-force**
   - Риск: чрезмерная нагрузка/подбор.
   - Исправление: добавлены scoped DRF throttles `auth_login` и `auth_2fa_verify`.

## 2) Что всё ещё спорно/нужно улучшить

1. **Email/SMS канал 2FA пока stub**
   - Нужен production интегратор (SMTP/SES, Twilio и т.д.).

2. **Антивирусная проверка базовая (EICAR)**
   - Для production нужен внешний AV (ClamAV/ICAP/облачный сканер) и асинхронный quarantine-flow.

3. **GEDCOM парсер ограничен базовыми тегами**
   - Нужны полноценные источники, семьи, браки, топонимы, aliases, custom tags.

4. **UI современный, но нужен UX-research с пользователями 50+**
   - Проверить контраст, размеры шрифтов, сценарии «большого дерева».

## 3) Приоритетный план улучшений (как клиенту/бизнесу)

1. Production 2FA delivery + мониторинг доставки.
2. Полный audit trail по всем критичным сущностям + export отчётов.
3. Политики backup/restore с регулярной проверкой восстановления.
4. Нагрузочное тестирование API и графа дерева.
5. Улучшение onboarding и импорт мастера (CSV/GEDCOM + валидации).
