# Family Tree Platform — концепт, архитектура и план развития

## 1) Продуктовое видение

**Идея:** создать совместную платформу для построения семейного древа, где каждый участник добавляет известную ему ветвь и приглашает родственников для расширения истории семьи в глубину и ширину.

**Ключевая ценность:**
- не просто "рисовалка дерева", а **коллективная семейная база знаний**;
- подтверждаемая информация (источники, версии изменений, роли участников);
- эмоциональная ценность: фото/видео/истории, памятные даты, семейные линии и контекст эпохи.

---

## 2) Роли и права доступа

### Основные роли
1. **Владелец дерева (Owner)**
   - создаёт дерево, задаёт настройки приватности;
   - назначает модераторов;
   - управляет приглашениями и правами.

2. **Редактор ветви (Branch Editor)**
   - добавляет/редактирует родственников в разрешённых ветвях;
   - загружает медиа, добавляет исторические заметки.

3. **Комментатор/наблюдатель (Viewer/Commenter)**
   - просмотр дерева;
   - комментарии, предложения правок.

4. **Генеалог-эксперт (опционально, платная роль)**
   - проверяет данные;
   - помогает найти архивные источники;
   - выстраивает гипотезы происхождения.

### Модель доступа
- **Tree-level permissions**: доступ ко всему дереву;
- **Branch-level permissions**: доступ только к определённой ветви;
- **Person-level privacy**: скрытие чувствительных данных живых людей (например, дата рождения частично, контакты полностью скрыты).

---

## 3) Функциональные блоки MVP (первая рабочая версия)

### A. Аккаунт и onboarding
- регистрация (email + пароль, позже OAuth);
- подтверждение почты;
- создание первого дерева мастером-опросником;
- быстрый импорт "себя + родители + бабушки/дедушки".

### B. Построение дерева
- узлы людей: ФИО, пол, даты, места, статус (жив/умер);
- связи: родитель-ребёнок, супруги;
- визуализация дерева (панорамирование, масштаб, фильтры);
- отметка неопределённости (пример: "предположительно").

### C. Совместная работа
- приглашения по ссылке и email;
- права на редактирование;
- журнал изменений (кто, что, когда изменил);
- soft moderation: "предложить изменение" вместо немедленного применения.

### D. Контент по человеку
- **Историческая справка** (текстовая биография);
- **Медиа-галерея**: фото и видео;
- документы (сканы свидетельств, писем, военных архивов и т.д.);
- привязка источников к фактам (source citations).

### E. Поиск и навигация
- глобальный поиск по имени/фамилии/году/месту;
- фильтр по линии (материнская/отцовская);
- карта миграций (базово: список мест и лет).

---

## 4) Что добавить сразу в архитектуру (чтобы не переделывать через год)

1. **Версионирование фактов**
   - каждый факт хранится с историей изменений;
   - можно откатиться к любой версии;
   - конфликт-резолв при одновременном редактировании.

2. **Событийная модель**
   - события: рождение, брак, переезд, военная служба, эмиграция, смерть;
   - каждое событие имеет дату, место, описание, источники, медиа.

3. **Источник как сущность**
   - архив, ссылка, документ, свидетель, книга;
   - уровень доверия источнику;
   - факт может иметь несколько источников.

4. **Готовность к multi-tenant**
   - один пользователь может участвовать в нескольких деревьях;
   - логическая изоляция данных между деревьями.

5. **API-first подход**
   - весь функционал веба доступен через API;
   - это позволит безболезненно добавить Android/iOS клиенты.

---

## 5) Рекомендуемый технологический стек

## Backend
- **Python + Django + Django REST Framework**
  - зрелая экосистема;
  - удобно быстро запускать сложную доменную модель;
  - понятный admin для внутренних операций и модерации.

- БД: **PostgreSQL**
  - надёжная реляционная модель;
  - JSONB для гибких метаданных;
  - хорошие возможности для сложных запросов.

- Фоновая обработка: **Celery + Redis**
  - генерация превью медиа;
  - отправка приглашений/уведомлений;
  - периодические задачи (бэкапы, индексация).

- Файловое хранилище: S3-совместимое (MinIO/S3)
  - медиа, документы, аватары;
  - presigned URL для безопасной выдачи.

## Frontend Web
- **React + TypeScript + Next.js** (или Vue/Nuxt, если команда сильнее там)
  - SSR/ISR для скорости;
  - хорошая интеграция с API;
  - удобно делать богатый UI дерева.

- Визуализация дерева:
  - d3.js / React Flow / Cytoscape (выбрать после прототипа);
  - отдельный слой layout-алгоритмов (чтобы легко менять библиотеку).

## Mobile
- **Шаг 1 (быстро):** PWA + адаптивный web UI;
- **Шаг 2 (Android first):** Kotlin + Jetpack Compose, подключение к тем же API;
- **Шаг 3 (кроссплатформа):** Flutter/React Native по метрикам продукта.

> Unity для такого типа продукта обычно избыточен: тяжёлый runtime, сложнее поддержка бизнес-UI, хуже time-to-market для контентной платформы.

## 6) Архитектура данных (ядро домена)

### Основные сущности
- `User`
- `Tree`
- `TreeMembership` (роль пользователя в дереве)
- `Person`
- `Relationship` (тип связи)
- `Event`
- `Place`
- `Fact`
- `Source`
- `MediaAsset`
- `Invite`
- `ChangeLog`

### Важные принципы
- связь хранить **явно** (не вычислять на лету только по полям);
- даты поддерживать как точные, так и интервальные/неопределённые;
- все чувствительные поля отмечать уровнем приватности;
- мягкое удаление (`is_deleted`) для восстановления и аудита.

---

## 7) UX и "нескучный" дизайн

1. **Режимы просмотра дерева**
   - классический;
   - хронологический (таймлайн семьи);
   - географический (карта перемещений).

2. **Story cards**
   - карточки "История человека" с фото, ключевыми событиями, цитатами;
   - автогенерация "Семейного альбома" по эпохам.

3. **Смысловые подсказки**
   - "У этого человека нет места рождения";
   - "Ветка обрывается на 1890-х — предложить родственнику добавить".

4. **Геймификация без инфантилизма**
   - индикатор полноты ветви;
   - достижения за подтверждённые источники;
   - ежемесячный семейный дайджест.

5. **Доступность**
   - крупные зоны клика;
   - контрастные темы;
   - поддержка пожилых пользователей.

---

## 8) Генеалогическая методология (профессиональный аспект)

1. **Классы достоверности фактов**
   - A: подтверждено документом;
   - B: подтверждено несколькими свидетелями;
   - C: семейное предание без источника.

2. **Исследовательский workflow**
   - гипотеза → источник → факт → ревью → публикация в дереве;
   - конфликт фактов решается через карточку спора, а не удалением.

3. **Нормализация имён и топонимов**
   - девичьи фамилии отдельно;
   - исторические названия мест + современные эквиваленты;
   - учёт вариантов транслитерации.

4. **GEDCOM совместимость**
   - импорт/экспорт GEDCOM;
   - это важно для миграции пользователей из других сервисов.

---

## 9) Безопасность и правовые аспекты

- JWT + refresh tokens, ограничение сессий;
- 2FA для владельцев деревьев;
- шифрование чувствительных данных (где нужно);
- rate-limit на приглашения и публичные endpoint'ы;
- полная audit trail для административных действий;
- GDPR/локальные нормы: право на удаление, экспорт данных, согласие на обработку.

## 10) Поэтапный roadmap (реалистичный)

### Этап 0 — Discovery (2–3 недели)
- интервью с целевой аудиторией (семейные архивисты, обычные семьи, диаспоры);
- прототип UX дерева;
- согласование доменной модели.

### Этап 1 — MVP (8–12 недель)
- аккаунты, дерево, базовые связи;
- приглашения и роли;
- исторические заметки + фото;
- web-версия + mobile-friendly интерфейс.

### Этап 2 — Совместное качество данных (6–8 недель)
- источники, уровень достоверности;
- журнал изменений и предложенные правки;
- улучшенный поиск и фильтры.

### Этап 3 — Масштабирование и mobile app (8–12 недель)
- Android приложение через API;
- оффлайн кэш для просмотра;
- push-уведомления и семейные дайджесты.

### Этап 4 — Дифференциация (долгосрочно)
- AI-помощник для извлечения данных из документов (OCR/NER);
- автоматические подсказки потенциальных совпадений персон;
- платные экспертные проверки генеалогов.

## 11) Что лучше сделать прямо сейчас (практический старт)

1. Зафиксировать **доменную схему** и API-контракты в OpenAPI.
2. Поднять Django-проект с PostgreSQL и базовой auth/roles моделью.
3. Реализовать минимальный UI дерева (CRUD персон и связей).
4. Добавить хранилище фото/документов и базовые правила приватности.
5. Сразу включить audit log и версионирование фактов.

---

## 12) Критические риски и как их снижать

1. **Рост хаоса в данных**
   - лечится строгой моделью источников, ревью и правами.

2. **Сложный UX при большом дереве**
   - виртуализация графа, режимы фильтрации, lazy rendering.

3. **Конфликты между родственниками по данным**
   - система версий + карточки споров + арбитраж владельцем.

4. **Юридическая чувствительность персональных данных**
   - приватность по умолчанию для живых людей, аудит доступа.

---

## 13) Монетизация (если проект коммерческий)

- Freemium: базовое дерево бесплатно, расширенные функции по подписке;
- Pro-тариф: неограниченные медиа, расширенная аналитика, экспорты;
- Маркетплейс генеалогов/архивных исследований;
- семейная печать: генерация "книги рода" в PDF/печать.

---

## 14) Рекомендуемое решение по мобильной стратегии

**Оптимальный путь:**
1. Web (Django + modern frontend) как основной продукт;
2. API-first с первого дня;
3. Android-клиент вторым этапом, когда подтвердятся метрики удержания;
4. кроссплатформу выбирать после проверки юнит-экономики.

Это даёт минимальные риски, быстрый запуск и хорошую основу для масштабирования.
